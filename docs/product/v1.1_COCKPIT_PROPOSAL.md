# v1.1 Proposal — Cockpit Operator Experience

Status: **PROPOSAL — not authorized.** Raised 2026-07-18 after a review question
("the cockpit demo looked very different"). Written to the post-GA governance
contract: Objectives · Scope · Risk · Verification · Release notes · Rollback.

Repository is frozen at `v1.0.0-rc.1` (commit `a7e397f`). Post-freeze rules
exclude UI work, so nothing here proceeds without an explicit founder decision.

---

## 0 · The decisive fact, first

The polished cockpit in `prototypes/va1/cockpit.html` was **never validated**.
The programme's own record says so:

- `X1_SYNTHESIS_00_NO_EVIDENCE.md`: *"Zero X1 sessions have been run. Zero human
  beings have been observed."*
- Hypothesis matrix: **0 validated · 0 disproven · 9 untested.**
- H4 ("Cockpit calm under pressure") specifically: *"Not tested — instrument
  gap … hold-Space gavel never exercised."* Naïve-operator testing was deferred
  to VA-2, which never ran.

So the prototype is a **beautiful, untested hypothesis** — not evidence. Rebuilding
the shipped cockpit to match it would be exactly the "speculative engineering"
and "architecture rewrite without evidence" the closure directive forbids, and
would break a release freeze for a design bet nobody has confirmed.

**Therefore this proposal leads with getting the evidence, not with building.**

**The functional substrate is complete and certified.** The genuine gaps are
narrower than first stated, and are in the *operator interaction layer*:

| Gap | Evidence |
|---|---|
| G1 · No keyboard control | Zero `onKeyDown`/`keydown` handlers in any auction surface |
| G2 · Destructive action has no confirmation friction | `CloseLot` is a plain click; `useHoldGate` is built, tested, and its **only consumer is the gallery demo** |
| G3 · No single "next decision" focus | Operator scans a grid to find the next action |
| G4 · Borrowed visual identity | 3 cockpit-specific CSS classes vs 16 in the prototype; the rest reuses `registration-*` / `competitions-*` classes from other pages |

## 2 · Objectives

1. Determine — with real operators — whether the shipped cockpit is actually
   hard to run on auction night. (Answer H4 for the first time.)
2. Close the gaps that are defensible on **safety and ergonomics** grounds
   regardless of taste (G1, G2).
3. Only then, and only if evidence supports it, invest in visual identity (G4).
4. Change **zero** business logic, engine commands, capabilities, or schema.

## 3 · Plan — three tiers, gated

### Tier 0 — Evidence (do this first; ~1 day, no code)

Run the naïve-operator test that never happened, against the **shipped** cockpit,
not the prototype.

- 3–5 people who have run or helped run a tournament. Instruction: *"run the next
  five lots."* No coaching.
- Reuse the existing instruments: `X1_RESEARCH_PROTOCOL.md`,
  `OBSERVATION_SHEET_TEMPLATE.md`, and the evidence ledger in
  `docs/phase-0b/x1-evidence/` (empty and waiting).
- Measure what H4 defined: missed decisions, hunting for controls, time-to-
  action, self-reported control, any need for rescue.
- **Exit:** either "operators are fine" (close this proposal; the difference was
  aesthetic) or a ranked list of real failures that scopes Tier 2.

Cost is trivial next to the alternative, and it converts opinion into evidence —
which is precisely the governance we agreed.

### Tier 1 — Safety & ergonomics (defensible without new evidence)

Small, low-risk, arguable on their own merits today:

- **G2 — hold-to-close the lot.** Route `CloseLot` through the existing
  `useHoldGate` (`{ progress, bind }`, already unit-tested, reduced-motion safe
  by design: motion changes presentation, never duration). Closing a lot is the
  one irreversible-feeling act on the night; a plain click is thin protection.
  *Undo already exists and stays untouched.*
- **G1 — keyboard control.** `O` open next lot · `Space` hold to close · `P`
  pause/resume, over the **existing commands**, plus a visible legend. An
  operator drives this surface for hours; mouse-only is an objective ergonomics
  and accessibility gap.

Non-destructive by construction: taps stay available, the destructive action
requires a hold, and no command semantics change.

### Tier 2 — Operator model & identity (gated on Tier 0)

Only if Tier 0 shows real operator difficulty:

- **G3 —** a "next decision" panel deriving one primary action from existing
  snapshot state (`scheduled` → Open auction; `live` + no lot → Open next lot;
  lot open → Hold to close; `paused` → Resume; queue empty → Complete). Pure
  derivation from state the client already has — no new state, no new reads.
- **G4 —** a dedicated `.cockpit-*` CSS vocabulary replacing the borrowed
  `registration-*` / `competitions-*` classes, decoupling cockpit styling from
  unrelated pages.

## 4 · Scope boundaries (non-goals)

- ❌ No changes under `packages/*` (frozen domains: core, auction, settlement, finops).
- ❌ No new engine commands, no command-semantics changes — the engine's acks stay authoritative.
- ❌ No schema change, no migration. (The old reason given here — "preserves the schema-free rollback property" — no longer applies: 0015–0026 shipped after RC-1 and migrations are forward-only. The real reason stands on its own: a cockpit UI change has no business touching the schema, and a release with no migration is the one case that rolls back by image swap alone.)
- ❌ No new capability, grant, or permission.
- ❌ No changes to stage / spectate / owner surfaces.
- ❌ No wholesale port of the prototype's fonts/colour direction — Direction A vs B
  was itself an untested A/B (H6), so "just use the prototype's look" would be
  adopting an unresolved experiment.

## 5 · Risk assessment

| # | Risk | Sev | Mitigation |
|---|---|---|---|
| R1 | Keyboard shortcuts fire while typing in a field | High | Ignore when the event target is `input`/`textarea`/`contenteditable`; explicit test. |
| R2 | `Space` collides with native button activation | High | Handler scoped to the cockpit root; `preventDefault` only when the gavel is the intended target; test both paths. |
| R3 | Accidental irreversible action via keyboard | High | The destructive path (`CloseLot`) requires a **hold**, never a tap; `UndoLastAction` remains. |
| R4 | Regression in the certified live-auction flow | High | `live-auction.spec.ts` + `conduct-ceremony.spec.ts` must pass **unchanged** — they are the safety net, not to be edited to fit. |
| R5 | Accessibility regression | Med | axe already runs on cockpit surfaces and must stay green; keyboard is an *addition* — every action keeps a visible control. |
| R6 | Reduced-motion violation | Low | `useHoldGate` alters presentation only, never duration (documented + tested). |
| R7 | Breaking the freeze for taste | **Med-High** | This proposal exists to force that decision explicitly. Tier 0 first; Tier 2 gated on evidence. |
| R8 | Scope creep into a console-wide redesign | Med | Non-goals above are binding; cockpit only. |

## 6 · Verification

- Existing certified suites pass **unchanged**: live-auction, conduct-ceremony,
  auction-foundation, auction-experience.
- New permanent coverage: keyboard-shortcut unit tests (incl. the typing-in-field
  and Space-on-button cases), a hold-gate integration test proving a tap does
  **not** close a lot and a completed hold does.
- axe clean on the cockpit; reduced-motion honoured.
- Full gate: typecheck · lint · prettier · depcruise (incl. `no-circular`) ·
  unit · integration · e2e · production build.
- Manual: two-browser live auction (the engine requires ≥2 claimed paddles and
  ≥1 queued lot to go live).

## 7 · Release notes (draft)

> **v1.1.0 — Cockpit operator experience.** The auction cockpit gains keyboard
> control (`O` open next · `Space` hold to close · `P` pause/resume) and a
> hold-to-confirm gavel, so closing a lot takes a deliberate press rather than a
> single click. No change to auction rules, money, or permissions.

## 8 · Rollback plan

- No migration, so rollback is a **pure app-image swap** — the property v1.0.0
  established is preserved by the non-goals above.
- Roll back if: any certified auction e2e fails, an operator reports an
  unintended lot close, or axe regresses.
- Tier 1 and Tier 2 ship as **separate releases** (v1.1.0, v1.2.0) so either can
  be reverted without losing the other.

## 9 · Recommendation

**Do Tier 0 now. Do not start Tier 1 or 2 yet.**

The honest position: we do not currently know that the shipped cockpit is a
problem. It is functionally complete, certified, and connected to a real engine;
what it lacks against the mockup is an interaction model and a visual identity
that **no user has ever validated**. One day of operator observation either
retires this question or gives it a real mandate — and that is a far better use
of the next engineering hours than reverse-engineering an untested prototype.

If a decision is needed before any beta operator sits down, **Tier 1 alone** is
defensible today on safety and ergonomics grounds, at genuinely small risk.
